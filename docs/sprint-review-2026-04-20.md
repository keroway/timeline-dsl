# スプリントレビュー 2026-04-20

## 全体方針（マネージャー視点）

前スプリント（2026-04-19）でコードベースの品質・仕様書の整合性を回復させた。
今スプリントは「内部品質の維持」から「外部への価値提供」にギアを切り替える。

ユーザーからの3つの要望（CLIリリース配布 / レンダリングリッチ化 / WebUI編集画面）を受け取り、
優先度を精査した上で今スプリントのスコープを確定した。

## 要件定義フェーズ（2026-04-20）

### ユーザー要望の受領

以下の3要望を受領し、優先度・依存関係・実現可能性を評価した。

| 要望 | 内容 | 評価 |
|------|------|------|
| 要望1 | CLIコマンドとしてリリース可能にする（curl \| sh 形式でインストール） | **最優先** |
| 要望2 | 描画のリッチ化（スケール・配色・カスタムCSS） | **今スプリント** |
| 要望3 | WebUI編集画面（新規作成・アップロード・ビジュアル編集） | **将来スプリント** |

### 優先度判断の根拠

#### 要望1（CLIリリース）を最優先とした理由

tdsl の利用者として想定する「年表の作者（ライター・研究者・教育者）」は、
Rust ツールチェーンをインストールしていないケースが多い。
`cargo build` が前提の現状は、ツールとして完成していても**事実上使えない**状態に等しい。

配布インフラは他のすべての価値提供（WebUIを含む）の土台となる。先行して完了させるべき。

#### 要望2（レンダリングリッチ化）を今スプリントに含めた理由

- `tdsl render` コマンドは既に動作しており、CLIオプション追加・CSS拡充は独立した作業として実施可能
- 配色・テーマ対応は WebUI プレビューの品質にも直結するため、早期対応が後のスプリントを楽にする
- `RenderOptions` の拡張は既存アーキテクチャへの自然な延長線上にあり、リスクが低い

#### 要望3（WebUI）を今スプリントのスコープ外とした理由

1. **技術前提の未確定**: wasm か HTTP API か、FE フレームワーク、ホスティング先が未決定
2. **配布インフラ未整備**: WebUI バックエンドに tdsl-core が必要。#34 完了後に整理すべき
3. **作業量過大**: 最低2〜3スプリント分の見積もり。中途半端な実装は UX を損なう
4. **依存関係**: #35（レンダリング）の品質がそのまま WebUI プレビュー品質になる

**推奨着手順序**: #34 → #35 → #28（キャッシュ）→ #36（WebUI）

### 追加提案（マネージャー判断）

要望には含まれていないが、Issue #28（Wikidata キャッシュ）は前スプリントからのバックログとして
引き続き優先度が高い。今スプリントで #34/#35 が順調に進んだ場合、後半に取り組むことを推奨する。

## テクニカルリスクと対策

### install.sh の信頼性

- **リスク**: GitHub API のレートリミット・ネットワーク障害により install.sh が失敗する
- **対策**: ダウンロード失敗時に明確なエラーメッセージを出力し、代替手順（直リンク）を案内する

### musl 静的リンクのバイナリサイズ

- **リスク**: tdsl-cli + 依存クレートの総バイナリサイズが 20MB を超える可能性
- **対策**: `cargo build --release` の前に `strip`・`opt-level = "z"` を検討。`cargo bloat` で依存確認

### RenderOptions の API 変更

- **リスク**: `wrap_html` のシグネチャ変更が `tdsl-cli` 以外の利用者に影響する
- **対策**: `RenderOptions` は既に public API。`Default::default()` で後方互換性を維持する
