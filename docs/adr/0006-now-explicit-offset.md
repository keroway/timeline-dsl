# ADR 0006: `now` への明示的 UTC オフセット付与

- **Status**: Proposed（設計検討・issue #647 のスコープ内。実装 GO/NO-GO は本 ADR のレビュー後に別途判断する）
- **Date**: 2026-07-21
- **Deciders**: keroway（レビュー待ち）
- **Related issues**: #647（本 ADR）
- **Supersedes**: なし。ADR 0003「秒精度＋タイムゾーンのデータモデル」の「未決定事項」冒頭にある「`now` に明示的な offset・タイムゾーン名を持たせるかどうかは将来の別 issue」（`docs/adr/0003-second-precision-and-timezone-offset-data-model.md` 122〜126行目）への回答として位置づける。ADR 0003 の D1〜D6（決定済み事項）は変更しない。

## コンテキスト

ADR 0003（#611〜#616, v1.27.0 で実装済み）は `TimeValue` に `DateTimeSecond` / `DateTimeOffset` / `DateTimeSecondOffset` の3 variant を追加し、offset 付き値同士を UTC 正規化して比較する `MixedOffsetComparison` ロジックを導入した（D1〜D3、`crates/tdsl-core/src/lower/mod.rs`）。一方、DSL の `now`（現在時刻を指すキーワード、open-ended range の終端等で使用）はこの精度拡張の対象に含まれておらず、依然として「年」精度でのみ解決される。

`now` に明示的な UTC オフセットを付与できるようにすべきか（例: レポート生成時のタイムゾーンをタイムライン著者が明示したい場合）は、ADR 0003 では意図的に持ち越された。

## 検討事項

### 1. `now` の現状の解決粒度

現状の実装（v1.27.0 時点）を確認する必要がある。ADR 0003 は `now` 自体の精度拡張を対象にしていないため、`now` は年精度のまま据え置かれている可能性が高い。もし `now` に offset を付与する機能を検討するなら、まず `now` 自体を秒精度・`DateTimeSecond` 相当まで拡張するかどうかという、より基礎的な設計判断が先に必要になる。**本 ADR 単体では `now` の解決粒度そのものを変更しない**（別 issue でのスコープとする）。

### 2. 構文案

| 案 | 例 | 評価 |
|---|---|---|
| `now` に直接 offset サフィックスを付与 | `now+09:00` | ADR 0003 D1 の precision-tag 拡張パターン（`TimeValue` の variant 追加）と一貫性があるが、`now` はリテラル値ではなく評価時に解決される特殊トークンであるため、既存の「値+offset」文法（`2024-01-01T00:00:00+09:00` 等）とパーサレベルでの扱いが異なる可能性がある |
| 専用キーワードで区別 | `now_utc` / `now(+09:00)` | `now` 自体の文法を変えずに済むが、キーワードが増える（`keywords.json` の更新対象が広がる） |
| offset 付与をサポートしない | — | 最もシンプル。`now` は常に UTC で解決し、比較が必要な場合は呼び出し側（表示レイヤー）でオフセット変換する運用にする |

### 3. 意味論: instant シフト vs 注記のみ

`now+09:00` のような構文を仮に採用する場合、2通りの意味論があり得る:

- **instant シフト**: `now` が指す瞬間（UTC epoch）はそのままで、表示・比較時に `+09:00` のオフセットを付与するだけ（「今」という値自体は変わらない）。
- **注記のみ**: offset は単なるメタデータであり、`now` の値そのものには影響しない（比較ロジックにも影響しない）。

ADR 0003 D2 の `MixedOffsetComparison`（offset の有無が混在する比較を明示エラーとして拒否する設計）と整合させるなら、「instant シフト」の解釈が自然である。「今」という瞬間は offset に関わらず一意であり、offset は表示上の時差だけを表すべきである。この点は ADR 0003 の既存設計（offset は「いつを指すか」ではなく「どう表示するか」の情報であり、UTC 正規化して比較する）と一致する。

### 4. ADR 0003 を supersede するか、追記するか、新規 ADR にするか

- ADR 0003 の D1〜D6 は「静的な時刻リテラル」への秒精度・offset 付与を扱っており、`now`（動的に解決されるトークン）は対象外だったことが本文からも明確（「未決定事項」に明記されている）。
- したがって ADR 0003 を **supersede する必要はない**。本 ADR（0006）を新規に立て、ADR 0003 の未決定事項への回答として参照する形が適切。

## 決定事項

### D1. 本 ADR の時点では実装方式を確定しない（Proposed のまま）

`now` 自体の解決粒度（年精度のまま据え置くか、秒精度に拡張するか）が未確定である以上、offset 付与の構文・意味論を先に確定させることはできない。本 ADR は検討軸の整理に留め、実装は別issueへの分割前に、まず「`now` の解決粒度をどうするか」を扱う先行issueが必要であると結論する。

### D2. 実装が GO となった場合の設計指針（申し送り事項）

1. 意味論は「instant シフト」を優先候補とする（3節参照、ADR 0003 D2 との整合性が高い）。
2. 構文は既存の precision-tag 拡張パターン（`TimeValue` への variant 追加、ADR 0003 D1）を踏襲することを優先候補とする。ただし `now` がリテラルではなく評価時解決トークンである点を踏まえ、パーサ・AST 設計時に既存の `DateTimeOffset` 系 variant とは別の設計単位（例: `NowWithOffset` 相当）が必要かどうかを実装着手時に再検討する。
3. `now` 自体の解決粒度拡張（年→秒）とセットで設計するか、独立した issue に分けるかは、実装着手時にスコープを再確認する。

## 比較した代替案

| 方式 | 判定 | 理由 |
|---|---|---|
| 本 ADR で構文・意味論まで確定する | ❌ 不採用 | `now` の解決粒度という前提が未確定であり、構文だけを先に固定すると手戻りリスクが高い |
| 検討軸整理 + 申し送り事項に留める（採用） | ✅ 採用 | 前提条件（`now` の解決粒度）を明確にした上で、次の設計フェーズに正確な出発点を渡せる |
| `now` への offset 付与自体を却下する | ❌ 不採用 | 需要（レポート生成タイムゾーンの明示）自体は issue #647 の起票理由として残っており、却下は本 ADR の権限外（プロダクト判断が必要） |

## 既知リスク

- `now` の解決粒度拡張とセットで議論しないと、offset 付与の意味論だけが宙に浮いた設計になる可能性がある。
- implementation-strict.md §2 NO-GO（MVP deferred機能の実装）に該当するため、実装着手前には必ずユーザー確認が必要。

## 未決定事項（本 ADR の範囲外）

- `now` 自体の解決粒度（年精度のまま据え置くか、秒精度に拡張するか）。
- 構文の最終決定（`now+09:00` / `now(+09:00)` / 専用キーワード等）。
- パーサ・AST・IR・lowering・renderer・decompile・CSV・LSP・WASM の各層への実装方式。
