# ADR 0007: IANA タイムゾーン名対応の是非

- **Status**: Proposed（設計検討・issue #648 のスコープ内。実装 GO/NO-GO は本 ADR のレビュー後に別途判断する）
- **Date**: 2026-07-21
- **Deciders**: keroway（レビュー待ち）
- **Related issues**: #648（本 ADR）
- **Supersedes**: なし。ADR 0003「秒精度＋タイムゾーンのデータモデル」の「未決定事項」および D6（`docs/adr/0003-second-precision-and-timezone-offset-data-model.md`）で「IANA タイムゾーン名（`Asia/Tokyo` 等）による DST 自動解決は対象外。offset は数値（分単位）のみを扱う固定オフセットモデル」と明記された方針の再評価として位置づける。

## コンテキスト

ADR 0003（#611〜#616, v1.27.0 で実装済み）は、時刻の UTC オフセットを「数値（分単位）の固定オフセット」としてのみ扱うデータモデルを採用した。IANA タイムゾーン名（`Asia/Tokyo` 等）による DST（夏時間）自動解決は明示的にスコープ外とされている。

本 ADR は、この方針を維持するか、IANA タイムゾーン名対応を追加するかを判断するための材料を整理する。

## 検討事項

### 1. 技術選択肢

| 選択肢 | 概要 | 主な影響 |
|---|---|---|
| A. 対応しない（現状維持） | 固定オフセットモデルのまま。DST が必要な場合は著者がタイムライン内で期間ごとに offset を明示する運用を継続 | 追加コストなし。ADR 0003 D6 の既存方針を追認するのみ |
| B. `chrono-tz` 等の外部クレートに依存 | IANA tzdata を組み込み、タイムゾーン名から DST を含む実オフセットを自動解決する | 新規依存追加（バイナリサイズ増加、tzdata の定期更新が必要）。WASM ターゲット（`tdsl-wasm`, WebUI）へのバンドルサイズ影響が懸念される |
| C. 固定 offset のタイムゾーン名エイリアス辞書を自前実装 | `Asia/Tokyo` → `+09:00`（DST なし固定）のような簡易マッピングを自前で持つ | 外部依存を増やさずに済むが、DST 対応地域（多くの欧米タイムゾーン）では不正確になり「タイムゾーン名を名乗るが DST を無視する」という中途半端な仕様になる。誤解を招くリスクが高い（implementation-strict.md §1「Explicit error over silent fallback」の精神に照らすと、不正確な自動解決は避けるべき） |

### 2. ADR 0003 D6（外部日時クレート非依存方針）との整合性評価

ADR 0003 は独自の時刻パース・比較ロジックを採用し、`chrono` 等の汎用日時クレートへの全面依存を避ける設計を取った（D6、実測結果セクション参照）。理由として、WASM バンドルサイズへの影響と、必要な機能（年〜秒精度 + 固定 offset）が限定的であるため自前実装で十分だった点が挙げられる。

- **選択肢 B（`chrono-tz` 依存）は ADR 0003 D6 の方針と正面から衝突する。** `chrono-tz` は IANA tzdata 全体（数百 KB 規模）を埋め込むため、WASM バンドルサイズへの影響は「軽微」では済まない可能性が高い。WebUI（`apps/webui`）が WASM 経由でコンパイラを呼び出す構成である以上、この影響は実測なしに看過できない。
- **選択肢 C（自前エイリアス辞書）は依存追加を避けられるが、正確性を犠牲にする。** DST を無視した「タイムゾーン名っぽい何か」を提供することは、ユーザーに誤った期待を持たせるリスクがあり、strictness 原則（実装方針ルール §1「Strictness over permissiveness」）に反する。

### 3. 需要の再検討

IANA タイムゾーン名対応が必要になる典型的なユースケースは「異なるタイムゾーンのイベントを1つのタイムラインに混在させ、DST の影響を自動的に正しく扱いたい」場合である。既存の `examples/global_conference_timezones.tdsl`（#612〜#616 実装時のサンプル）は、複数タイムゾーン（`+09:00` / `-05:00` / `Z`）を固定オフセットとして明示する運用で既にこのユースケースをカバーしている。DST をまたぐ長期タイムライン（例: 同一都市の夏季・冬季イベントを跨いで比較する場合）でのみ、固定オフセットモデルの限界が顕在化する。

## 決定事項

### D1. 現時点では選択肢 A（対応しない）を推奨する。ただし最終決定は本 ADR のレビュー後に確定する

- 選択肢 B は ADR 0003 D6 の既存方針（外部日時クレート非依存、WASM バンドルサイズ配慮）と衝突するため、採用するなら ADR 0003 D6 を明示的に見直す必要がある。バンドルサイズへの実測影響評価なしに依存追加を決定すべきではない。
- 選択肢 C は不正確な DST 扱いによりユーザーに誤解を与えるリスクが高く、strictness 原則に反する。
- 選択肢 A は、既存の固定オフセットモデルと `examples/global_conference_timezones.tdsl` が示す運用パターンで大半のユースケースをカバーできており、需要が限定的な機能拡張のために D6 の方針を覆すコストに見合わない。

### D2. 選択肢 B を将来的に検討する場合の条件（申し送り事項）

もし将来 `chrono-tz` 依存の要望が具体化した場合、GO 判断の前に以下を実測すること:

1. `chrono-tz` を `tdsl-wasm` に追加した場合の WASM バンドルサイズ増分（gzip 後のサイズで比較）。
2. `tdsl-core` のみに `chrono-tz` を追加し、`tdsl-wasm` は依存しない構成（機能を CLI 限定にする）が可能かどうかの技術的検証。
3. 上記1が許容範囲を超える場合、feature flag で `chrono-tz` 依存をオプトインにできるかの検討。

implementation-strict.md §2 NO-GO（MVP deferred機能の実装）に該当するため、選択肢 B/C いずれを採用する場合も着手前にユーザー確認が必須である。

### D3. 対応しない（選択肢 A）が最終決定となった場合の対応

- AGENTS.md §5 の「IANA time zone names ... — see ADR-0003 未決定事項」という記載を「ADR-0007 で対応しない方針を確定」に更新する。
- ADR 0003 の「未決定事項」からこの項目を除去し、ADR 0007 への参照に置き換える。
- これらのドキュメント更新は、本 ADR のレビューで D1 が承認された後、軽微な docs-only PR として別途実施する。

## 既知リスク

- 選択肢 A（対応しない）を確定した後にニーズが再燃した場合、選択肢 B のバンドルサイズ実測（D2）を改めて行う必要があり、再調査コストが発生する。
- 本 ADR の技術評価（`chrono-tz` のバンドルサイズ影響）は実測ではなく一般的な知見に基づく推定であり、D2 の実測なしに B/C を正式に却下したとは言えない。D1 は「現時点で採用する決め手がない」という消極的な結論であり、積極的な「今後も対応しない」という恒久的決定ではない。

## 未決定事項（本 ADR の範囲外）

- 選択肢 A/B/C のうちどれを最終的に採用するかの正式決定（本 ADR のレビュー後に確定）。
- 選択肢 B を採用する場合の `chrono-tz` 依存範囲（`tdsl-core` 限定か、`tdsl-wasm` まで含めるか）。
- 選択肢 C を採用する場合のエイリアス辞書の具体的な収録範囲・更新運用。
